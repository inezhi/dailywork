## 为什么单独记

同一条规则会同时影响：数据库列、API 字段、事件 payload、用例表。
口头定完就忘，三个地方各写各的，最后对不上。所以每条决议记四样：

- **决议**：一句话结论
- **影响**：动哪些东西
- **飞书现状**：PRD 里写了没有
- **待办**：还差什么

## D1 完成父任务 ↔ 子任务

**决议**：完成父任务时，其子任务跟着完成；执行前弹二次确认。

**影响**：

- `TaskCompleted` 的消费逻辑：谁是消费者、消费到什么程度
- 用例表：`CompleteTask` 多一个分支
- API：需要一个显式参数（如 `cascade: true`），不能靠服务端猜

**为什么必须显式传参**：确认是 UI 的事，服务端看不见。
如果服务端自作主张联动，用户点了"取消"也拦不住；
如果服务端等前端再发一次请求，就不是"一个用例"了。
所以确认结果要落到请求参数上，服务端按参数执行。

**机制上的两条硬约束**（来自第 6 课）：

1. 联动不在 Task 聚合内部做。父任务和子任务是两个独立聚合，聚合看不见别的聚合。
   做法：父任务在自己的事务里完成 + 写 outbox；消费者对**每个子任务各开一个事务**。
2. 消费者必须幂等。事件会重投，同一条子任务被完成两次不能出错。

**中间状态**：父任务完成、部分子任务还没跟上，这段时间是可见的。
可接受，因为失败会重试，超上限进 DLQ；但不能接受的是"永不收敛"，所以要监控 DLQ。

**飞书现状**：02 PRD 的 FR-T3 只定义了任务自身进入/离开 `done` 时 `completedAt` 的写法，
没有父任务联动的规则。

**待办**：

- [x] 写进 02 PRD 的 FR-T3，明确只联动**未完成**的子任务，已完成的保持不变
- [x] 定参数名与默认值（`cascade`，默认 `false`，即不联动）
- [x] 写进 07 契约：`POST /tasks/{id}/complete` 与 Thrift `CompleteTask` 的 `cascade`

## D2 删除父任务 ↔ 子任务

**决议**：级联删除，二次确认。

**影响**：

- `TaskDeleted` 事件、软删策略、API 错误码
- 今天查询的过滤条件

**飞书现状**：已改。FR-T4 现在是"删除父任务前提示子任务数量，用户确认后级联软删除子任务；
父子写入同一个 `deleted_at`，保留 30 天"。

**技术上的一个取舍**：级联删除要改 N 个 Task 聚合，和"一个事务只改一个聚合"冲突。

| 做法 | 好处 | 代价 |
|---|---|---|
| 父任务删 → 发 `TaskDeleted` → 消费者逐个删子任务 | 守住聚合边界 | 中间态：父任务已删、子任务还在，今天页可能露出孤儿 |
| 一条 SQL 批量软删（`WHERE id = ? OR parent_id = ?`） | 原子、简单、无孤儿 | 一次事务改了多个聚合 |

两者都是同一服务、同一张表，第二个代价是理论上的。

**已定（2026-10-31，写进 06）：** 日常删除用一条 SQL 批量软删，同一张表、原子完成；
30 天后的物理清理才 `DELETE`，由 `fk_tasks_parent` 的 `ON DELETE CASCADE` 兜底删子任务。
外键不参与日常级联——软删除根本不触发它。这样既没有孤儿窗口，也不用为一个可接受的
理论代价去引入事件驱动的一致性等待。

**待办**：

- [x] 02 PRD 把"（需确认）"改成"删除前提示子任务数量，用户确认后级联"
- [x] 确认软删：写 `deleted_at`，两边同一时间戳，保留 30 天
- [x] 06 数据模型里定上面那个取舍（批量软删 + 物理清理靠外键）

## D4 "今天"的日期口径

**问题原本长这样**："今天只看 `scheduledDate`，还是为空时回落到 `dueDate`？"

**人话**：一个任务可以同时有两个日期——"我计划哪天做"和"哪天必须交"。
今天页按哪个把任务捞出来？如果按计划日期，那没填计划日期的任务就永远不出现；
如果为空时回落到截止日期，那一个昨天到期的任务今天还在。

**飞书已经回答了**，02 PRD 的 FR-D2：**两个都看，分在不同分组，同一个任务只进优先级最高的那组。**

| 优先级 | 分组 | 判定 |
|---|---|---|
| 1 | 逾期 | `dueDate < 今天` 且未完成 |
| 2 | 今天到期 | `dueDate = 今天` 且未完成 |
| 3 | 今天计划 | `scheduledDate = 今天` 且未完成 |
| 4 | 进行中 | `status = doing`，前三条都没捞到 |
| 5 | 下一步 | `status = next`，前四条都没捞到 |
| 6 | 今日完成 | `completedAt` 落在今天 |

所以不存在"回落到"这个设计——两个字段各自成组，不需要互为兜底。
一个昨天到期、今天计划、状态进行中的任务，只出现在"逾期"。

`今天` 一律由客户端传 `YYYY-MM-DD`，服务端不用自己的时区推导（FR-D1）。
验收里专门有一条：客户端日期和服务器 UTC 日期不同时，分组仍以客户端为准。

**待办**：无。已闭环。

## D5 归档 ↔ 今天

**决议**：归档后不出现在今天。

**飞书现状**：任务的六个状态是 `inbox / next / doing / waiting / blocked / done`，
**没有 `archived`**。`archived_at` 只出现在 06 数据模型的 spaces / projects 上。

所以原来的问法（"归档的任务还出现在今天吗"）在 v2.0 不成立——任务没有归档态。

**真正需要定的是**：归档**项目**下的任务，还出现在今天吗？

**建议**：不出现。归档的含义是"从默认视图移除"，不是"删除"：
任务本身还在，搜索和项目页里找得到，只是不参与今天页的默认分组。
否则归档就等于没归档——用户归档一个项目，今天页纹丝不动。

**待办**：

- [x] 02 PRD 补一句：归档项目下的任务不进入今天页的默认分组（FR-T7）
- [ ] 06 数据模型：今天查询要 join project 判断 `archived_at IS NULL`
- [ ] 术语表把 `Archive` 限定为"项目级操作"，不要写成任务状态

## D6 客户端形态

**决议**：v2.0 交付两种客户端——网页端（浏览器）与 macOS 桌面端（Tauri 2 外壳），
两者加载同一份 React 构建产物。Windows、Android、iOS 后续再纳入。

**为什么是 Tauri 不是 Electron**：前端已经确定是 React SPA，桌面端只需要窗口、菜单、
快捷键和启动检查。Tauri 用 macOS 自带的 WKWebView 渲染，包体 10MB 量级，不背 Node 运行时。
Electron 生态更熟，但包体 100MB 起，且要把 Node 工具链拉回来。

**为什么不给桌面端做专属页面**：一套页面两种投递方式，才不会出现"网页端改了、桌面端忘了改"。
桌面端多出来的只有外壳。

**飞书现状**：02 PRD 新增 FR-C1；01 §4.1/§4.3 改范围；03 M4 增加桌面端交付；
04 §2/§9 增加客户端链路与取舍；12 新增 §6.8 外壳规格；13 ADR-0019。

**待办**：

- [x] PRD 非目标从"桌面端"改成"Windows / Android / iOS 客户端"
- [x] M4 验收补：双击安装、免登录进入、后端未启动给提示

## D7 桌面端的登录态

**决议**：网页端继续用 `daily_session` HttpOnly Cookie；桌面端用 Bearer token，
存 macOS Keychain，请求由 Tauri 的 Rust 侧发出。

**为什么不复用 Cookie**：Tauri 的页面跑在 `tauri://localhost`，gateway 在
`http://localhost:8080`，是两个源。Cookie 要跨站发送就得 `SameSite=None; Secure`，
本地还得为它配 HTTPS 证书；WKWebView 对第三方 Cookie 的策略还在收紧。为一个个人工具
维护这条链路不划算。

**代价**：登录接口多一个 `X-Client: desktop` 分支，多一条凭证路径要写测试；
Keychain 不可用时要明确报错，不能静默失败。

**飞书现状**：09 §5.1 桌面端凭证；07 §1 认证约定与登录/注册/退出三行；
13 ADR-0020。

**待办**：

- [x] 契约里写清 `X-Client: desktop` 的行为（不下发 Cookie、响应体返回 token）
- [ ] 契约文件落地时，OpenAPI 里把这条写进 login/register 的响应与头部说明

## D8 部署形态

**决议**：开发阶段本地用 Docker Compose；开发完成后把整套服务部署到一台服务器，
用单节点 k3s 编排。访问入口见 D9。

**为什么不是服务器上也用 Compose**：Compose 更省事，但练不到 Deployment、Service、
Ingress、ConfigMap/Secret、探针、PVC、滚动更新与回滚——这些是大厂部署里最通用的语言，
也是这个项目"学习为主"想要的。本地留 Compose，是因为改一行代码不该等集群。

**服务对谁可见**：见 D9——不暴露公网，只有加入 tailnet 的自有设备能访问。

**飞书现状**：01 §4.1 运行环境与状态表、03 M6 整节重写（不再选做）、04 §7 部署拓扑与

## D9 访问入口

**决议**：服务器加入 Tailscale tailnet，所有外部访问走 tailnet，**不开任何公网入站端口**。
k3s 照旧用 Ingress，但只监听本机回环；宿主机上 `tailscale serve` 在 tailnet 内提供 443，
证书由 Tailscale 为 `*.ts.net` 自动签发和续期，cert-manager 不再需要。

**为什么推翻了"公网只开 443"**：那条 ADR 依赖两个前提——服务器能用 443、能控制域名 DNS。
实际环境只有第三方 FRP 中转给的一个随机端口，域名属于服务商，既不能加 DNS 记录也不能把
NS 交给 Cloudflare。于是 Let's Encrypt 三条验证路全断：HTTP-01 要 80，TLS-ALPN-01 强制
443，DNS-01 要 TXT 记录。Tailscale 把这些前提整个绕开。

**被放弃的两个方案**：

| 方案 | 卡在哪 |
|---|---|
| 继续用 FRP 承载 HTTP | 地址带随机端口；证书要么自签要么用服务商的；流量明文经第三方；服务商随时可能停服 |
| Cloudflare Tunnel | 要求域名 NS 托管到 Cloudflare，而域名不在自己手上 |

**代价**：每台设备要装 Tailscale 并登录，不属于自己的设备用不了；"公网可访问"这个目标取消；
依赖 Tailscale 的协调服务器（可自建 headscale 替代）。

**一条容易漏的安全细节**：Tailscale 只负责加密和寻址，**不会自动关掉服务器上的其他端口**。
宿主机防火墙必须显式默认拒绝，只放行 tailscale0 与受限 SSH，否则开了 tailnet 也照样暴露。

**飞书现状**：01 §4.1 状态表、03 M6（入口、边界安全、验收、学习重点）、04 §6 技术栈
与 §7 部署拓扑、09 §1/§10/§12、13 ADR-0023、14 §6 环境表与发布检查单。

**待办**：

- [x] 写进 13 ADR-0023，并把它作为 ADR-0022 的取代记录
- [x] 03 M6 的验收从"外网能打开"改成"tailnet 内能打开、网关上没有公网监听"
- [ ] 桌面端的服务器地址默认值等 M4 实现时再定（`https://<主机名>.<tailnet>.ts.net`）
