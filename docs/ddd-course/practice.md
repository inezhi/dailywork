## 检查题记录

### 第 5 课 · 战术设计

**学生答案**：1）OrderLine 是实体；Address 是值对象，可以改。2）存快照。3）动一个 Task 聚合。

**批改**：1、2 结论对但理由没答到点；3 答错。

**参考答案**

1. `OrderLine` 是实体：换掉数量和单价，只要行号（ID）没变，还是同一行——相等性看 ID。`Address` 是值对象：它没有身份，两份完全相同的地址互换无人能发现；而且它不可变，改了就是另一个地址，不是"同一个地址改过"。
2. 连名称和价格一起存快照。名称和价格的所有者是 Product 聚合，订单只是引用者；商品会改价改名，而订单要记录下单那一刻的事实。所以订单存 `productID` 引用 + 不可变快照。快照不是为了性能，是为了记录事实。
3. 要改**所有**引用该标签的 Task 聚合。一个标签可能被上千个任务引用，而一个事务只能改一个聚合——改 N 个做不到，只改一部分又不一致。所以 Tag 必须是独立聚合，Task 里只存 `tagIDs`。结论：共享数据不能放进聚合内部。

### 第 6 课 · 应用层

**学生答案**：1）写进 Task 聚合，应用服务只管流程。2）拆成两个事务，用事件关联。3）直接查询，不必成为实体。

**批改**：1 错；2 方向对、事务数不对；3 对，理由偏薄。

**参考答案**

1. 写在应用服务里，配合事件；不写进 Task 聚合。父任务和子任务是两个独立的 Task 聚合，聚合看不见别的聚合，没有能力回答"我的子任务现在什么状态"。写进聚合只有两条路：塞一个 `children` 集合，退回大聚合；或者持活子对象，边界当场破。正确拆法："完成"的定义留在 Task 聚合（`done` ⇔ `completedAt`），"完成后要不要动子任务"交给应用服务编排，用 `TaskCompleted` 事件驱动子任务在自己的事务里处理。
2. 事务数是 1 + N：事务① 改 Project 并写 outbox 发事件；消费者对**每个 Task 各开一个事务**。失败重试，超上限进 DLQ，处理必须幂等。还要明确中间状态是否可接受——不能接受就重新设计这个用例。
3. 三条理由任取两条：① Today 没有不变量，"今天"是查询条件不是状态；② 提前存等于两份真相，任务、日期、时区一变就要重算，漏一次就不知道哪份是对的；③ 会把时区钉死，我们的约定是业务日期由客户端传 `YYYY-MM-DD`，服务端不推导"今天"。

### 第 7 课 · 契约

**学生答案**：1）不需要，加的是可选字段，不影响兼容。2）算破坏性变更，新增一个字段，保留老字段。3）同一个小区两栋楼，直接用会带上很多不需要的字段和逻辑。

**批改**：1 对；2 判定和做法都对，缺过渡期管理；3 半对，理由偏浅。

**参考答案**

1. 不需要升 `/api/v2`。可选 + 只加不删 = 兼容：老客户端收到不认识的 `archivedAt` 会忽略。只要不新增必填、不改已有字段含义、不改类型，`/api/v1` 就不用动。唯一要确认的是客户端有没有做严格反序列化（遇到未知字段报错）。
2. 算破坏性变更，做法是 expand / contract：先加 `statusDetail: {code, changedAt}`，旧的 `status` 继续写（双写）；消费者逐个迁移；确认没人读旧字段后才删。删旧字段才是真正要换 topic 版本的那一步。两个补充：① 历史事件回放时同一份代码会同时遇到新老两种形状，过渡期内必须都认；② 没有监控就没有"确认没人读了"，旧字段会永远留着。
3. 根本原因不是"字段太多"，是"边界挡的是变化，不是数据量"。三条按重要性：① 领域模型是内部实现，直接 import 后上游重构会让下游编译失败或行为悄悄改变；② 两个上下文里的 Task 不是一个意思——task 里它是有状态机、受不变量保护的聚合，assistant 里它只是一条只读引用，import 会把"能改"也带过去，等于能绕过上游规则；③ 共享模型就是共享内核，是耦合警告，两边会一起变。"字段多"只是窄契约的好处，不是根本原因。

### 第 8 课 · 实现

**学生答案**：1）搭起来没有联调。2）不含鉴权，因为它不是最小的设计。3）端到端通了就行：能落到数据库、能正常返回、能正确处理逻辑。

**批改**：1 半对，答了现象没答机制；2 结论对，理由空转；3 只答了一条，另外三条和"为什么代码写完不算"都没答。

**参考答案**

1. 不是"没联调"这么简单。骨架是每个服务**单独**跑得起来，看起来完成了；真正的风险是一串从未被验证的集成假设——超时、协议、时区、错误码、鉴权传递、数据归属。按层推进把这些假设全部推到最后**同时**接受检验，集中爆发在项目最没有余量的时刻。更糟的是进度表一直显示正常，形成假的完成感。
2. 不要鉴权。第一刀要验证的假设只有一个：HTTP → RPC → ORM → 迁移这条基础设施是对的。加进 identity 之后，失败时你分不清是链路问题还是鉴权问题。硬编码 ownerID 是一个**可回退的临时决定**，要写下来并设好移除条件——第二刀换掉。
3. 四条，缺一条都算没做完：能演示（curl 走完整条链路）、有测试（领域单测 + 仓储集成测试）、有指标（`/healthz`、`/metrics`、带 `request_id` 的日志）、文档同步（契约与飞书文档同一次提交）。"代码写完"不算，因为它是"我做了"，不是"它能用"：没有测试和日志，下一次改动时你不知道坏了没有；文档没同步，契约和实现对不上，下一刀就要踩。
