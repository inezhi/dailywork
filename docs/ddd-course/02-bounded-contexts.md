# 第 2 课：限界上下文

> 状态：已讲完
> 外部案例：Jimmy Bogard 的 Texas 司法系统项目复盘（The DDD Do-Over）
> 关键词：限界上下文、模型边界、同名不同义、语言边界、翻译层

## 1. 现实问题：同一个 “offense”，两个部门说的不是一回事

Jimmy Bogard 在 2017 年的 Explore DDD 演讲里，复盘了两个很相似的项目。

第一个项目是 Texas 州的青少年司法案件管理系统。用户是分散在多个县、多个机构的州政府员工，覆盖青少年案件从立案到处理的整个流程。团队按 DDD 的常规做法做了实体、聚合、repository，也建了通用语言。系统上线了，客户也满意。

但几年后回头看，它变成了一个单体：模型越来越大，改一处要动很多地方。

问题出在一个很常见的词上：**offense**（违法行为，也可以理解为案件或罪名）。

- 执法人员说 offense 时，关心的是：发生了什么、涉及谁、要不要立案、由哪个机构跟进。
- 检察官说 offense 时，关心的是：能不能起诉、罪名是什么、证据够不够、走哪个程序。

两个部门都同意用 “offense” 这个词，开会时没人反对。但散会后，各自心里的字段、规则、状态是不一样的。

Bogard 在复盘里说：

> Both law enforcement and prosecutors have a concept of an “offense.” In our actual system, we partitioned the two concepts so that there were two “offense” domain objects — one for law enforcement, and one for us. Keeping them separate meant that we could grow each independently of the other.

## 2. 解决方式：先划边界，再决定哪些模型可以共用

第一个项目的问题，不是 DDD 做错了，而是把“同一个词”当成了“同一个模型”。

当两边共用一个 `Offense` 模型时，会发生这些事：

- 为了同时满足两边，模型不断加字段；一边要的字段另一边用不上，只能留空。
- 规则变成一堆条件：`if 机构 == ...`、`if 阶段 == ...`。
- 一个机构改规则，另一个机构的流程要跟着回归测试。
- 新机构加入，再加一层条件。
- 最麻烦的是：大家以为在讨论同一个东西，其实在讨论两个东西，会议很难收敛。

Bogard 在第二个项目里换了做法：先划边界，再分别建模型。

- 执法上下文：一个 `Offense` 模型，包含立案、执法机构、调查状态等。
- 检察上下文：另一个 `Offense` 模型，包含罪名、起诉决定、证据状态等。
- 两边用 ID 关联，不共享类或表；需要对方数据时，通过接口取，并在边界上翻译。
- 外部模型的字段、状态、术语进入本上下文时，先转换成自己的模型，不让外部模型直接流进来。

这样每个模型只服务好自己的上下文，规则不会被另一边的需求污染，两边可以独立演进。

## 3. 概念：限界上下文

> 限界上下文是一个模型生效的边界。在这个边界内，同一个词只有一个含义、一套规则；出了边界，同一个词可以有另一个含义、另一个模型。

三个要点：

- 边界内：一种语言、一个模型、一套不变量。
- 边界外：同名不同义是正常的，不是错误。
- 跨边界：显式翻译，不共享内部模型。

它不是什么：

- **不是一个微服务。** 一个上下文可以部署在一个服务里，也可以跨多个服务；一个服务也可以包含多个上下文。
- **不是一个团队。** 团队组织可以变，模型边界由语言和规则决定。
- **不是一个数据库。** 数据库是存储边界，上下文是模型边界；两者经常对齐，但不是一回事。

## 4. 理论：问题空间 vs 解决方案空间

- 第 1 课的子域是**问题空间**：业务上有哪几块问题。
- 限界上下文是**解决方案空间**：我们为这块问题建了一个什么样的模型，这个模型在哪里有效。
- 两者通常一一对应，但不保证：
  - 一个子域可能需要多个上下文：同一块业务，对不同用户群用不同模型（比如执法人员 vs 检察官）。
  - 一个上下文也可能覆盖多个子域：如果它们共享同一套语言和模型，硬拆反而增加翻译成本。
- 通用语言只在上下文内通用。出了边界，同一个词不需要保持同一个意思。
- 上下文之间的关系（谁依赖谁、怎么翻译）是下一课的内容：上下文地图。
- 一个实用判断：如果两个团队对同一个词的定义需要反复开会对齐，而且每次对齐完还会变，通常说明这里有一条上下文边界。

## 5. 闭环：我们项目的上下文

| 上下文 | 核心模型 | 这个词在这里指什么 | 出了边界怎么用 |
|---|---|---|---|
| `task` | Task、Project、Space、Tag | 有状态机、完成时间、父子关系的工作项；有归档规则的项目 | 只传 ID，或调 task API |
| `identity` | Account、Session、Credential | 登录身份、密码、会话 | 其他服务只存 ownerID，不存账号详情 |
| `docs` | Document、Block、Backlink | 文档树、正文块、反向链接 | 只存 taskID 引用，不复制任务内容 |
| `assistant` | Conversation、Message、ToolCall | 对话、消息、工具调用 | 通过 task API 读写任务，不直连 task 数据库 |
| `gateway` | — | 不是上下文；HTTP 入口、鉴权、协议转换 | 不承载业务模型 |

同一个词，在不同上下文里：

| 词 | `task` 上下文 | `assistant` 上下文 | `docs` 上下文 |
|---|---|---|---|
| task | 有 status、completedAt 的聚合，有 `Complete()`/`Reopen()` | 用户对话里提到的一件事，是意图或参数 | 文档里的一行待办文本，或一个块 |
| user | `ownerID`，只存 ID | 对话的用户，只是身份引用 | `authorID`，只存 ID |
| project | 有归档规则的任务容器 | 对话的作用域或参数 | 文档里可能是一个文件夹，不是 Project 聚合 |

具体规则：

- `assistant` 要完成一个任务：拿到 taskID，调 task 的接口；task 服务负责状态机和不变量的校验。assistant 不复制 Task 模型，也不直接改 task 数据库。
- `docs` 要展示任务：存 taskID，按需调 task API 取摘要；不做跨库 JOIN。
- `identity` 是账号的唯一来源；task、docs、assistant 只保存 ID，不复制密码、邮箱等账号字段。

每个上下文的一句话定义：

- `task`：负责空间、项目、任务、标签及其状态规则；不负责登录、文档正文、AI 对话。
- `identity`：负责账户、密码、会话、验证码；不负责任务和文档。
- `docs`：负责文档树、正文块、反向链接；不负责任务的业务规则。
- `assistant`：负责对话、工具调用、流式输出；不直接拥有任务数据。
- `gateway`：负责 HTTP 入口、鉴权、限流、协议转换；不是业务上下文。

## 常见问题：两个模型就要两张表吗？

不一定。模型边界不等于表边界。

- 一个上下文内部可以有多张表：聚合表、outbox、读模型。
- 两个上下文也不一定各建一张表：如果一边只读，可以由拥有方提供查询、视图或 API，另一边翻译成自己的模型。
- 真正决定存储的是：**这份数据谁负责写、谁负责改、要不要在同一个事务里改。**

判断顺序：

1. 两边都要写同一份数据吗？都要写，通常说明边界没划清，或者需要拆数据所有权。
2. 两边要在同一个事务里改吗？要，可能它们还是一个聚合或一个上下文。
3. 两边独立演进吗？独立演进、独立部署，通常各自拥有存储，用 ID 关联，跨边界走 API 或事件。
4. 字段和规则差异大吗？只差几个字段，可能是一个模型加子类型；差异大，才值得拆两个模型。

映射到我们的项目：

- `task` 和 `assistant` 在两个服务、两个数据库：`task` 拥有任务表；`assistant` 在自己的库里存 `task_id`，通过 task API 读写，不做跨库 JOIN。这不是“两个模型所以两张表”，而是“一个服务一个数据库、数据有明确所有者”。
- `task` 上下文内部也不止一张表：任务、项目、标签、outbox 各管各的。
- 所以不要用“表的数量”判断上下文数量；用“谁拥有这份数据、谁定这套规则”判断。

Bogard 的文章没有讲他具体建了几张表。能确定的是：两个 `Offense` 模型各自表达一套字段和规则，边界上通过 ID 和翻译交互；具体落到一张表、两张表还是两个库，是存储设计，不是 DDD 的定义。

两个上下文共用一张表，通常会出这些问题：一边加字段，另一边被迫兼容；迁移互相阻塞；权限和写入责任不清。所以多数情况下，共用表是边界没划清的表现。

## 检查题

1. Bogard 的案例里，执法和检察都说 “offense”。如果只建一个 `Offense` 模型给两边用，会出现哪些具体问题？为什么拆成两个模型后反而更好维护？
2. 我们项目里 `task` 和 `assistant` 都会说“任务”。它们是同一个模型吗？`assistant` 要完成一个任务时，应该怎么和 `task` 交互？

## 本课总结

- 限界上下文是模型生效的边界，不是服务、团队或数据库。
- 边界内一种语言、一个模型、一套规则；边界外同名不同义是正常的。
- Bogard 的案例：执法和检察的 “offense” 字段、规则、生命周期不同，所以保留两个模型，各自演进。
- 强行共用一个模型，会用可空字段和条件分支把两边绑死；一边改，另一边跟着坏。
- 跨边界用 ID、API、事件和翻译层，不共享内部模型；上下文之间怎么协作是下一课的内容。

**关键词**：限界上下文、模型边界、同名不同义、语言边界、翻译层。
